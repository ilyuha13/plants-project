# Backend: интеграционные тесты

Запуск из корня проекта:

```sh
pnpm --filter @plants-project/backend test:run
```

Требования: установленные зависимости (`pnpm install`), работающий локальный
PostgreSQL и отдельная база `plants_test`, принадлежащая роли `plants_test`.
Обычные локальные и production-данные не используются. Схема приложения не изменена.

## Первичная настройка

Подключившись к локальному PostgreSQL под пользователем с правами создания ролей
и баз, выполните один раз (если такой базы и роли ещё нет):

```sql
CREATE ROLE plants_test LOGIN PASSWORD 'plants_test_local'
  NOSUPERUSER NOCREATEDB NOCREATEROLE;
CREATE DATABASE plants_test OWNER plants_test;
```

Скопируйте `backend/.env.test.example` в `backend/.env.test` и при необходимости
укажите свой пароль и порт. На компьютере, где создавалась эта задача, база,
роль и файл уже подготовлены. `.env.test` исключён из Git.
Пример пароля предназначен только для отдельной локальной тестовой роли.

## Что делает запуск

1. Проверяет TEST_DATABASE_URL до любых подключений и изменений.
2. Генерирует Prisma Client из текущей схемы (важно после переключения веток).
3. Применяет существующие миграции через `prisma migrate deploy`.
4. Запускает файлы `src/**/*.test.ts` последовательно, без `dist` и скриптов.
5. Перед каждым тестом и в конце файла очищает перечисленные в setup таблицы
   в порядке зависимостей. После аварийного завершения данные уберёт следующий запуск.

Разрешены только localhost/127.0.0.1/::1, база `plants_test`, роль `plants_test`
и схема `public`. Адрес не должен совпадать с рабочей базой из окружения,
корневого `.env` или `backend/.env`, даже при разных паролях и схемах.
Произвольные параметры подключения запрещены, чтобы нельзя было подменить host.
Не используйте `plants_test` для ручной работы: её содержимое расходное.
Не запускайте два процесса тестов одновременно против одной базы.

Приложение использует фиктивные переменные окружения. Telegram заменён заглушкой,
а глобальный fetch отклоняет запросы. Подключение PostgreSQL настоящее.
Тесты не запускают HTTP-сервер или фоновые задания.

## Покрытые правила

- отказ неавторизованному пользователю;
- чтение своей корзины и запрет удаления чужой позиции;
- конкурентное добавление одного экземпляра в разные корзины;
- одно оформление при двух одновременных checkout;
- полный откат checkout при недоступности одной позиции;
- удаление свободного экземпляра администратором;
- запрет удаления обычным пользователем, из корзины или из истории заказа;
- отмена с сохранением истории;
- защита экземпляра в другом активном заказе или корзине при отмене;
- проверка допустимых и запрещённых адресов тестовой базы.

## Как добавить сценарий

Используйте фабрики из `src/__tests__/helpers.ts`, вызов `callerFor(user)` и
проверяйте как ответ обработчика, так и итоговые записи в базе. Идентификаторы
генерируются автоматически. Не рассчитывайте на данные другого теста.

Тестовый router объединяет настоящие обработчики корзины и заказов. Проверяется
их tRPC-авторизация, валидация, Prisma и транзакции. Не проверяются HTTP/JWT,
браузерный интерфейс, доставка уведомлений, cron, гостевая корзина или весь MVP.
Для конкурентных сценариев используются два реальных запроса через Promise.allSettled;
это проверка конкуренции, но не исчерпывающий перебор всех возможных расписаний.

Проверки перед коммитом:

```sh
pnpm types
pnpm lint
pnpm --filter @plants-project/backend test:run
```

Production-сборка `pnpm --filter @plants-project/backend build` очищает старый
`backend/dist` и использует `tsconfig.build.json`, исключающий тесты и их helpers.
Общая проверка `pnpm types` по-прежнему проверяет типы тестов.
Docker также исключает тестовые исходники через `.dockerignore`.
